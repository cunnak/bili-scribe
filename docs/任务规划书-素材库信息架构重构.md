## 1. 背景与目标

### 1.1 现状（全部为现读读数，命令附在 §9）

用户原话：「素材库分类太乱了」。拆开是三件事：

| 现象 | 实测读数 | 根因 |
|---|---|---|
| 找不到具体某一条 | 73 条平铺在一条时间线里 | 只有「阶段」一个维度，没有来源维度 |
| 不知道下一步做什么 | 60 条 `downloaded` 堆在一起 | 阶段桶不可用作待办清单 |
| 合集被拆散 | 63 条属于 5 个 `collection_title`，其中「2026正大杯备赛」39 集、「【从零开始的 AI 学习】」21 集 | 前端从未按合集归组 |

真正的 P0 缺陷（今天就发生，不是 201 条才发生）：

- `ui.js` 的 `STAGES` 有 **8** 个阶段，`library.js` 的 `STAGE_FILTERS` 只暴露 **6** 个，筛选是 `row.stage === key` 精确匹配。
- 实测库内 stage 分布：`downloaded 60 / new 5 / analyzed 3 / summarized 3 / transcribed 2`。
- ⇒ **6 条（analyzed 3 + summarized 3）在六个桶里一个都选不出来**；六桶之和 67 ≠ 总数 73。
- 同时「已切片」桶永远为 0（`clipped` 无任何写入方），`analysis` 分支里引用的 `"analyzed"` 在 Python 侧 0 命中。

第二处硬缺陷：

- `library.js` 的 `load()` 写死 `{limit: 200, offset: 0}`，`service.library_list` 又把上限夹在 200；`summary.js` 的 `loadProjects` 同样传 200。
- ⇒ 第 201 条起不可达，且总结页的项目选择器一起被截断。73 条时不可见，是规模问题。

### 1.2 目标

1. 左栏从「一个阶段维度」变成「来源为树 + 阶段为 chips + 排序可选」的两级信息架构。
2. 阶段词表只有**一个 owner**，前端桶集合由后端 facets 驱动，`sum(facets) == total` 恒成立。
3. 「全部」列表可分页，201 条起可达。
4. 支持多选 + 批量转录 / 批量归档 / 批量移除；破坏性操作的数量与作用域在确认框里写清。
5. 归档：不进默认列表，保留记录与文件，可找回。
6. 合集内顺序可按「时间 / 标题 / B站合集顺序」切换。

### 1.3 非目标（本轮不做，别顺手加）

- 标签（tags）、评分、智能视图自定义、拖拽排序。
- 引入「导入批次」表。
- `collection_id` 的写入与回填（第二阶段另开卡）。
- `clip_cover_upload` 的路径边界收紧（另开卡，安全侧已记录）。
- 其他四个页面（subtitles / clips / summary / publish）的同类 200 上限问题，除 `library.list` 默认参数兼容外不动。

## 3. 方案总览

### 3.1 数据模型变化（仅两列，不加表）

```sql
-- v5
ALTER TABLE wb_project ADD COLUMN archived_at TEXT;      -- NULL = 未归档；ISO 时间 = 归档时刻
ALTER TABLE wb_project ADD COLUMN collection_index INTEGER; -- B站合集内的顺序（0-based）；NULL = 未知
```

两列都可空、都无默认值以外约束 ⇒ 旧版二进制读到多出的列会被 `SELECT *` 忽略，回滚安全。

### 3.2 阶段词表的单一 owner

新增 `video_workbench/core/stages.py`：

```python
STAGE_ORDER = ["new", "downloaded", "subtitle", "transcribed",
               "summarized", "clipped", "merged", "published"]
STAGE_LABELS = {"new": "待转录", "downloaded": "已下载", "subtitle": "有字幕",
                "transcribed": "已转录", "summarized": "已总结", "clipped": "已切片",
                "merged": "已合并", "published": "已发布"}
def stage_label(key: str) -> str: ...
```

- `core/recovery.py` 改为 `from .stages import STAGE_ORDER`（保持模块属性可 patch，不复制第二份）。
- `app/service.py` 的 `library_list` 返回 `facets: [{key, label, count}] ` + `stage_labels`。
- `web/js/components/ui.js` 的 `STAGES` 保留（其他页面还要用），但**新增一条机械闸**：JS 里出现的 stage 字面量必须 ⊆ `STAGE_ORDER`（见 T4-2）。

### 3.3 接口变化（全部向后兼容）

```python
class ListParams(BaseModel):
    query: str = ""
    limit: int = 50
    offset: int = 0
    stage: str = ""            # 新增，默认空 = 不过滤（等于现状）
    sort: str = "created_desc" # 新增，默认 = 现状的 created_at DESC
    include_archived: bool = False  # 新增，默认 False（但注意：现网没有 archived 行，行为不变）
```

返回体只增字段，不改旧字段：

```
{ items, total, limit, offset,
  facets: [{key,label,count}],      # 同 query + 同 exclude_archived 下按 stage 分组
  stage_labels: {key: label},
  archived_total: N }
```

**不变量（必须写成断言）**：`stage == ""` 时 `sum(facets[*].count) == total`。

新增 RPC：

| RPC | 入参 | 返回 | 说明 |
|---|---|---|---|
| `library.archive` | `{ids: [...], archived: bool}` | `{changed: N, skipped: [{id,reason}]}` | 单条/批量共用 |
| `library.delete_preview` | `{ids?} 或 {query?, stage?}` | `{total, with_draft, with_clip, with_candidate, sample_titles: [...]}` | 确认框的数据源 |
| `library.delete_many` | `{ids?} 或 {query?, stage?}`, `expect_total` | `{removed: N, skipped: [...], snapshot_path}` | `expect_total` 与服务器现算不符 → `CONFLICT`，不删 |

## 7. 回滚方案

1. **数据**：T0-1 保证每次版本升级前自动备份到 `<db>\.bak-<stamp>`；迁移失败即中止、不写入。
2. **代码**：本次改动集中在 6 个文件（`core/stages.py` 新增、`core/recovery.py`、`core/resolver.py`、`infra/db.py`、`infra/repo.py`、`app/service.py`）与前端 1 个文件（`web/js/pages/library.js`）+ `web/js/components/ui.js`（仅新增标签兜底）。回退 = 还原这些文件。
3. **库**：旧版打开 v5 库只忽略新列，不需要降级脚本；`schema_version` 会被写回 4，再升级会重新补列（幂等）。
4. **归档误操作**：`library.archive(archived=false)` 一键恢复；归档不改磁盘。

## 8. 风险登记

| # | 级别 | 风险 | 触发 | 缓解 |
|---|---|---|---|---|
| R1 | **P0** | 迁移写坏用户的 `bili-scribe.db` | 加列时 DDL 出错 / 新列 `NOT NULL` 无默认 | 阶段 0 全部完成；T0-3 dry-run 先看；新列全部可空 |
| R2 | **P0** | 全选语义把 200 当 1000 | 前端拿 `items.length` 当总数 | `expect_total` 服务端校验，不符即 CONFLICT |
| R3 | P0 | 批量删除半删 | 单条 `DELETE` 循环 | T1-8 单事务 + ROLLBACK |
| R4 | P1 | 搜索 + 阶段过滤因 OR 无括号而漏行 | 追加 `AND stage=?` 时 | T1-2 同笔加括号，用例钉住 |
| R5 | P1 | 分页无 tie-breaker 导致重复/丢行 | 同秒创建 + offset 翻页 | `ORDER BY ... , id DESC`；合成库 6 行同秒测两页 |
| R6 | P1 | 批量操作触发事件风暴（删 50 条 = 50 次 load） | 逐条 emit | 批量 RPC 只 emit 一次 |
| R7 | P1 | 合集改名后组分裂 | `collection_title` 被单行更新 | 本轮按标题分组是已知代价；`collection_id` 回填放第二阶段 |
| R8 | P1 | 归档被 task 状态覆盖 | 误用 `status` | 用独立 `archived_at` 列（D5 已定） |
| R9 | P2 | 组内顺序被用户第二次投诉 | 老数据 `collection_index` 全 NULL | T3-1 回填；NULL 排最后并显示「顺序未知」；真不行再按标题数字前缀排序 |
| R10 | P2 | 阶段词表再次漂移 | 未来加 stage 只改一处 | T4-2 机械闸 + `core/stages.py` 单一 owner |
