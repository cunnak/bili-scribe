## 这个版本解决什么问题

三件事，都是"用起来别扭"那一类。

**一、它一直是个网页。** 你得开一个控制台窗口看着服务日志，再切到浏览器标签页里操作；关控制台就把自己弄挂了。现在它是一个**独立的应用窗口**，双击就开，有任务栏图标，跟别的桌面程序一样。

**二、素材被重复买了好几遍。** 同一份素材的预读结果，只要换个任务重跑就得重买一次。真实账本里有个视频被重开成两个任务，两次各付约 13 万 prompt tokens 的完整预读，第二遍完全是白花。现在这份笔记会存下来，同一个视频再跑一次**一分不花**。

**三、界面太简陋。** 单页 HTML 里 207 行 CSS、五个编号卡片竖着堆。现在重写成了一个工作面。

## 现在是什么样

**一个窗口，没有端口。** 后端不再是"被 HTTP 调用的服务"，而是**同一个进程里的库**：界面直接调 Python 函数，进度由后端主动推给界面。

| | 旧（0.4.2） | 现在 |
|---|---|---|
| 前后端 | HTTP，监听 `127.0.0.1:8818` | 进程内调用，**不开端口** |
| 进度 | 页面每 1.2 秒轮询一次 | 后端主动推送 |
| 一个 110 秒任务 | 70–90 次 HTTP 请求，每次都回整块 JSON | 0 次轮询 |

轮询这一条值得说清楚：它不是"慢"的问题（本地 HTTP 往返毫秒级，占任务耗时 0.001%），是**白做**的问题——一个两分钟的任务里，页面要问七十多次"好了没"。

**界面是重写的。** 视觉取的是明日方舟那套工业 HUD 语言：近黑底 + 酸性黄绿强调 + 工业橙红只用于"需要你看一眼"和错误；等宽小字拉开字距做标签；刻度尺、斜纹、切角。信息架构从"五个编号卡片"改成**工作面**：顶部一条输入，主区只放当前任务，预览/版本/打磨/评论都在同一个可滚动面上，设置进侧边抽屉。

三层关系没变，只是多了一层壳：

```
desktop.py（窗口）      main.py（HTTP 路由，26 个，只做传输）
        └──────────────┬──────────────┘
                  app/service.py（业务，1382 行）
                            ↓
                    core/ → infra/
```

## 素材笔记：为什么落盘，以及它凭什么不会出错

`infra/notecache.py` 用**内容寻址**：`sha256(recipe + source_label + body)`，`recipe` 里含 `max_input_chars / chunk_size / chunk_overlap` 三个会影响产出的参数。参数一改，key 就变，不可能命中过期笔记。

**只在 `chunks > 1` 时写缓存。** 短素材根本不预读（`prepare_material` 在 `len(body) <= max_input_chars` 时原样返回），存进去只是占地方。

这是**零损优化**：命中就是省下一整段预读，未命中就退化成本来的行为，写缓存失败也只是下次重跑。没有任何一种失败会让产物变差——所以默认开启、不设开关，少一个配置项就少一处"忘了配"。

磁盘上是 `~/.bili-scribe/notes-cache/`，条目上限 300 条 / 192 MB，按 mtime 淘汰。**删掉整个目录等于清空缓存**，任务历史和版本史一点不受影响。设置页有清空按钮，并显示"本次命中 N 次 / 未命中 M 次"。

## 重新打包，以及一个坑值得记住

```bash
.venv\Scripts\python -m pip install pyinstaller
.venv\Scripts\python scripts\build-exe.py
```

出 `dist/bili-scribe.exe`，约 28 MB 单文件，不需要对方装 Python。

**`--windowed` 下 `sys.stdout` 和 `sys.stderr` 都是 `None`。** 这个项目的 `store` / `notes` / `bili` 三层日志全都接到 `print` 上，所以打包后任何一次日志都会抛 `AttributeError: 'NoneType' object has no attribute 'write'`。`desktop.py::_ensure_streams()` 在 `main()` 第一行把它们接到 exe 旁边的 `bili-scribe.log`（目录不可写时退到系统临时目录）——**接文件而不是丢弃，因为双击启动的 exe 恰恰最需要日志**。

**窗口句柄比画面先到。** 这不是 bug，但会让验证骗人：`tests/probe_exe.py` 第一版找到窗口就截图，得到一张纯黑图，而深色主题的底本来就接近黑，人眼很容易当成"设计就是这样"放过去。现在它会数颜色种类，够多了才开始截。

## 测试

```
python tests/smoke_test.py     # 37 项离线 + 35 项 HTTP
node tests/frontend_test.js    # 100 项前端
node tests/probe_http.js       # 源码版端到端：真起服务 + 真页面，全程 HTTP
python tests/probe_exe.py      # 打包产物实机验收
```

**前端测试是全部重写的。** 旧的 134 项做的是"读源码 → 正则抠出 `<script>` → 在 DOM 桩里求值 → 断言源码里出现过某段字符串"。它一直在报 PASS，测的却是拼写——页面脚本一碰 `addEventListener` 就抛异常，因为桩里没有它。现在换成 jsdom：真 DOM、真事件、真 await，断言的是**行为**（点了按钮会发生什么、界面变成什么样）。

旧用例没有保留，也没做兼容层。让测试骗自己是花钱买安心。

三条守底线的还在：页面里没有 `<input type=file>`（桌面版走原生对话框）、颜色对比度实际算出来（正文 ≥ 4.5:1）、以及**源码版那张 HTTP 路由表与后端逐个对账**。

路由表那条补得很值：桌面版走桥，源码版走表，表里名字拼错在桌面版永远暴露不出来（那条路根本不经过它），而源码版会安静地 404 或者更糟——退成默认值。补它的时候顺手抓到一个真 bug：`testLlm()` 写的是 `call("test_llm", { llm: values })`，多包了一层壳，后端收的就是那一层内部的字段，于是 422 报 `Field ["body","base_url"] Field required`——**错误信息指着字段名、不指着多出来的那层壳**，看着像配置写错。`testLlm` 从来没有被任何测试碰过，所以它一直坏着也没人知道。

笔记缓存也补了两条后端用例，其中「同一份素材跑两次只付一次预读」这条**先在旧实现上验过会红**：不传 `cache` 时第二次仍然跑 5 次预读。跑不挂的守护用例等于没写。

## 配置查找顺序变了

以前只认工作目录。exe 双击启动时工作目录不一定是 exe 所在目录（快捷方式可以指定"起始位置"，任务计划里更是随系统目录），按当前目录找会让人把配置写到莫名其妙的地方——表现就是"明明保存了下次打开又是空的"。

现在：**exe 旁边 → `~/.bili-scribe/config.yaml`**。便携版把配置跟着 exe 走，装机版放用户目录，两种都认，exe 旁边的优先。数据（库、密钥、笔记缓存）一律在 `~/.bili-scribe/`——凭据、库、配置本该待在一起。

## 安装

**桌面版**：下载 `bili-scribe.exe`，和一份 `config.yaml`（填上自己的 `llm.api_key`）放在一起，双击。

**源码版**：`python run.py`，和以前一样，仍然有 HTTP 服务与 `127.0.0.1:8818`，适合改代码和用 curl 调接口。

两种形态共用同一份 `~/.bili-scribe/`（任务历史、版本史、登录凭据原样沿用，无需迁移）。笔记缓存是新增的，第一次跑会全未命中，之后才开始命中。

---

**升级后先看窗口标题或底栏版本号是不是 `0.5.0`。** 桌面版更直接——exe 里冻的就是打包那一刻的代码，改了源码不重打包，版本号不会变。
