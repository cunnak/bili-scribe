v0.6.1：一个 exe 就能给对方用

起因是「能不能只发一个 exe，对方在里面填自己的 key」。查下去发现 exe 本身已经是
单文件、也不夹带任何密钥，但配置的落脚点有个会真出事的缺陷：`_default_config()`
原本的规则是「取第一个存在的，都不存在则取第一个候选」，那个候选就是 exe 旁边。
便携版没问题，装机版会踩坑——把 exe 拖进 `Program Files\`，或者从压缩包里直接
双击（解压在 `%TEMP%` 下的只读临时目录），exe 旁边根本写不进去。程序照旧选中那个
位置，用户认真填完 api_key 点保存，收到的是：

    配置写入失败：[Errno 13] Permission denied: '...\config.yaml.tmp'

看着像程序坏了，其实只是落脚点选错了。而这恰好是「只发一个 exe 给对方」最常见的
用法，所以必须修。

改法：新增 `_can_write_near()`，在「都不存在」这一步按可写性挑，而不是无脑取第一
个。判据是**目录存在且真能落盘**——真建一个探针文件再删掉，不用 `os.access`
（Windows 上它对 ACL 不可靠，主要看只读属性，这里要的是「到底能不能写进去」）。

三种情形都在测试里钉住了：

- 只读 → 退到 `~/.bili-scribe/config.yaml`
- 可写 → 仍然优先 exe 旁边，便携版「拷走 exe 就能带走配置」的心智模型不能丢
- 已存在 → 它压过可写性判断，否则用户自己写的那份会被忽略

测试用占位文件冒充只读目录（父路径是文件，`is_dir()` 为假），不依赖这台机器的实际
权限——以管理员身份跑测试时 `Program Files` 也能写，靠真实权限判会时灵时不灵。

顺带补上 `desktop.py` 缺的 `import os`。

关于「只发一个 exe」这个前提本身，实测确认：

- `dist/bili-scribe.exe` 是 `--onefile` 产物，28.2 MB，对方不需要装 Python
- 扫描 exe 字节：无 `sk-...` 形态的密钥，无 `api_key:`；源码 zip 85 个文件同样零命中
- 依赖 WebView2 运行时，Win10 1803+ / Win11 自带；只有 LTSC 和老机器会缺
- 单独拷进空目录启动，窗口正常（标题 `bili-scribe 0.6.0`），界面渲染完整，
  历史 78 条照常读——数据在 `~/.bili-scribe/`，与 exe 位置无关

测试：39 离线 + 46 HTTP，全部通过。
