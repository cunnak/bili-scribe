自 v0.3.0 以来是三件事：**无字幕时可以自己传 srt**、**不满意就反复改（带完整版本史）**、以及**把「模型说自己改了什么」变成「本地算出来改了什么」**。中间还修掉几个只在真实使用里才露头的 bug。

---

## 一、没有字幕的视频：自己传一份 srt

讲座、课程录像、老录像经常没有字幕，之前只能掉到弹幕档，总结质量随之下降。现在可以在主页选一份 `.srt`：**传了就用它**，平台字幕让位——但"平台其实有字幕"这件事会如实写进来源检查，不静默忽略。

- **选完立刻给回执**，不用等任务跑起来才知道文件对不对：`717 段，覆盖 00:00:00–01:59:23（编码 utf-8-sig）`
- **编码自动探测**：UTF-8（含 BOM）、gb18030／GBK、UTF-16、big5。回执里回显识别到的编码——出现乱码时那是唯一线索
- **不做 15 秒时间窗聚合**。聚合是为了救平台 AI 字幕（没标点、几字一行）；srt 通常已是规范整句，再粘合会把两句话拼成一句
- **能生成时间轴**：srt 自带真实时间戳，这是纯标题简介素材做不到的
- **两条错配校验，只警告不阻止**：覆盖时长不到视频一半、或末尾时间超出视频时长 1.2 倍。分段上传、只讲一部分的录像都是合法场景，但这类错误一旦发生会错得很隐蔽，所以必须让它出声
- **用完即删**：上传件落在临存区，任务结束删除（失败的也删），另有启动时与每个任务开始时的兜底

**一个无法消除的局限**：srt 里没有任何视频标识，程序**没有办法验证"这份字幕属于这条视频"**，只能比时长。两条时长接近的视频会校验通过，而模型会拿 A 的字幕去总结 B——这类错误不报错、读起来通顺，只有你自己发现"讲的内容对不上"才能察觉。

实现上值得一提的：解析是同步 CPU 操作，实测一份 5 MB 的 srt 要 0.5–0.8 秒，所以它被丢进线程池——否则会把事件循环上其他请求（含进度轮询）一起卡住。

## 二、迭代打磨：改到满意为止

第一次生成的总结不满意，就在预览页写一句"哪里不对"，点「再改一版」。**改完是新的一版，旧的都留着。**

**它刻意不是「重跑一次，顺便加个提示词」**，那样做有三个问题：

1. 提示词只改"怎么讲"，改不了"讲什么"。不满的根源若在素材层，加提示词会掩盖真实原因；
2. 每次全量重跑——4 小时视频一次 86,428 tokens；
3. **全局提示词会把你已经满意的部分也重写掉**，每一轮都在破坏上一轮的成果。

所以形态是「**素材 + 上一版 + 本次要求**」：模型看到完整的上一版 JSON 和要求，被明确告知只改需要改的地方。

**省下的是预读那一段。** 长素材要先分段预读，实测占一次 4 小时视频总结输入的 **32,663 tokens / 38%**。迭代时这份笔记直接复用：活体验证的轨迹里**没有 `mapping` 那一步**——不是耗时变短，是那一步根本没发生。

**素材笔记只进内存，版本史必须落库。** 前者丢了重新预读就能重建（只是贵一点）；后者丢的是劳动——靠重跑模型拿不回同一段文字。所以每一版（初版／每次迭代／每次回退）都进 `summary_version`，服务重启后一版不少，每版的全文、发布长文、当时的消耗、当时的要求都能查回来。

**回退不等于撤销。** 点「以这一版为底稿」是把那一版抄成**新的当前版**（版本号继续往前），而不是把指针挪回去——版本史要能如实回答"当时实际用的是哪一版"，这和 git revert 是同一种取舍。回退**不调模型**：实测 0.03 秒、零消耗。

**消耗是要看的。** 预览页常驻一行"累计 N 次模型调用 / 输入 X、输出 Y、合计 Z tokens"，每一版各自花多少也在版本列表里。不设硬上限（设了就变成"改到一半被拦住"），但让代价一直可见；端点不返回用量的调用会被单独点出来，不给一个漂亮的 0 蒙过去。

其它约束：**角色锁定**（换角色等于换个人重讲，得重新提交任务）；**改完重新要求你确认**（内容变了，"已确认"就不作数）；**入口只在发布前**（评论发出去不能编辑，要改先撤回）。

> 素材笔记的内存缓存留 200 条。这个数是**量出来的**：一条 39 KB（典型）、94 KB（最坏），200 条约 8–18 MB，而且**原素材不跟着进缓存**（实测把素材从 1.2 万字换成 60 万字，占用纹丝不动）。之所以不吝惜这点内存，是因为淘汰的代价是真金白银——重跑一条 4 小时视频要 86,428 tokens。

## 三、「实际改动」：不问它，自己比

`revise_note`（改动说明）是模型自己写的，实测**会不准**。所以版本列表里每一版现在有两行：

| 行 | 来源 | 性质 |
|---|---|---|
| 改动说明 | 模型自述 | 线索 |
| **实际改动** | 把这一版和上一版的 JSON 逐字段比一遍 | **事实** |

两者不一致时，以后者为准。三种状态分开说：**不显示**（没比过：第 1 版没有上一版，回退版没有"改"这回事）／**「无 —— 和上一版逐字相同（要求没被落实）」**（比过了、一个字没变，这本身就是信息）／逐字段列出（`正文（1279 → 1322 字，相似度 0.93）· 要点（6 项 → 6 项，其中 1 项内容不同）`）。

只报**内容字段**（一句话结论／正文／要点／时间轴／局限说明／短版）——`chunks`／`model`／`frames` 这些元信息变了不算内容改动，混进来会让每次比对都显示"改了一堆"，信号就没了。列表会额外说出"有几项内容不同"，因为最常见的情况恰恰是**项数没变、内容被换掉**。

想看具体差在哪里，把鼠标停在那一行上，或点列表上方的「**展开全部差异**」。

## 四、修掉的 bug（都是活体验收里抓到的）

1. **帧缓存的竞争：偶发的 `FileNotFoundError`。** 现象是迭代在 1.5 秒内失败，库里只留一句没有出处的报错，看起来像网络抖动。根因不是"删得早晚"，而是**两次采集共用了按 aid 命名的同一个目录**：主任务姗姗来迟的收尾会把迭代正在写的目录整个删掉。改成**每次采集独占目录**（`frames/<aid>-<随机>`，谁建谁删），竞争从构造上消失。实测复现率约 1/6。
2. **要求被自己的质量流程覆盖。** 要求写着"只改一个字段、其余一个字都别动"，而批判那一轮按角色自己的清单挑出七处毛病、修订那一轮照单全收——使用者的要求被覆盖掉了，从产出上完全看不出来。现在约束同时贴在批判与修订两轮上；活体验证里"只改 one_line、其余四个字段不许动"的结果是**那四个字段逐字未变**。
3. **报错丢掉了出处。** `{exc!r}` 不打 `.filename`，于是库里只剩 `FileNotFoundError(2, 'No such file or directory')`——报错进了库、界面也显示了，却没有任何线索指向哪一行。现在错误里带出最后两帧的「文件:行号 函数」，完整栈打到控制台。
4. **缓存失效的理由说错了。** 原来只说"程序重启过就会这样"，但缓存满被挤出去也会走到同一分支——对一个没重启过程序的人说"你重启过"，比不说更糟。现在两个原因都点明。
5. **`escapeHtml` 不转引号。** 它的结果会进 `title="..."` 这类属性，文本里一个引号就能把属性切开。
6. **缓存上限的依据错了三个数量级。** 原注释写"跑几十条就白占几百 MB"，实测 20 条只有 0.77 MB。上限本身从 20 提到 200，理由换成了量出来的数。

## 测试

```
python tests/smoke_test.py     # 32 项离线 + 35 项 HTTP
node tests/frontend_test.js    # 131 项前端
```

全部通过。除常规用例外，几条值得单说：

- **回归用例先在旧实现上跑一遍、确认它真的会红**。「画面文件的生死」把目录命名改回旧的共用方式必然失败；「淘汰顺序」换成漏掉 `pop` 的写法必然失败（否则就成了先进先出）；「报错指出出错的那一行」在旧实现下也必然失败。**跑不挂的守护用例等于没写。**
- 「上传解析不阻塞事件循环」断言的是**实现方式**（接口把解析交给了线程池）。我没找到稳定观测"事件循环有没有被阻塞"的办法，所以退一步做源码守卫。
- 活体验收（真实模型调用、真实库、真重启）三程都过了：老记录补写第 1 版、初版 + 两版迭代 + 回退、要求穿过三轮回、重启后版本史与全文完好。

## 一件要说清楚的事

**这个版本里关于模型行为的结论，样本量很小。** 「改动说明会不准」「只改提到的部分可被听到但不保证」这些判断，来自 **5 次真实迭代**，且都出自同一个模型、同一个角色、同一类视频。换一个模型或换一类内容，结论可能不成立。它们是**方向**，不是**速率**——功能本身（版本史、字段级比对、消耗可见）不依赖这些结论，但读那些话时请知道它们的分量。

## 安装

下载下方的 `bili-scribe-0.4.0.zip`，解压后按 `README.md` 操作。包内**不含**任何凭据、数据库或本机配置——打包脚本内置自检，且本次发布又用独立脚本复核了一遍（敏感文件名 0 命中；令牌、本机路径 0 命中；包内唯一出现的视频号是文档里的占位示例 `BV1xx411c7mD`）。

需要 Python 3.11+：

```
pip install -r requirements.txt
```

升级方式：解压覆盖，或 `git pull`。`config.yaml` 不在包里，不会被覆盖。
