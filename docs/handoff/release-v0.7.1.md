## 这个版本解决什么问题

**「发布记录」里那条撤回按钮，不是没了，是整块没画出来。**

反馈的原话是「历史发布功能里没有撤回按钮了」。第一反应是按钮被哪次改动删了——翻 git 记录，按钮从 v0.6.0 引入这块起就一直在，一行没动过。真正的问题在**取数**：界面拿到的那份列表里，压根没有这条视频的记录，于是整块 `display:none`，按钮跟着一起消失。

## 根因：取的是全局窗口，筛的是自己

`loadPublishes()` 原来这么写：

```js
const rows = await call("list_publishes", 12);          // 后端只回「全局最近 12 条」
const mine = S.publishes.filter((p) => p.bvid === S.task.bvid && !p.deleted_at);
```

后端 `list_publishes(limit)` 是 `SELECT * FROM publish ORDER BY id DESC LIMIT ?`——**不分视频**。前端拿到之后才按当前任务的 `bvid` 过滤。

于是：**别的视频一发得多，这条视频的旧记录就被挤出前 12 条**，过滤结果是空数组，`hist-blk` 被加上 `hidden`，连里面的按钮一起消失。

在本地库（38 条发布记录）上量的：

| 视频 | 原逻辑 | 修好后 |
|---|---|---|
| `BV1kPau6VEWb` | 可见 0 条 → 整块隐藏 | id 11 |
| `BV1v5eM6vELt` | 可见 0 条 → 整块隐藏 | id 5、1 |
| `BV1hBnC6ZEug` | id 33 | id 33 |

全局 top-12 只覆盖 6 个不同的 bvid。所以这个 bug 的表现是「越用越没有」：**早发的视频先掉出去，最近发的还在**。它也不是 v0.7.0 改出来的——v0.6.0 引入这块时就是这个写法，只是那时记录还没到 12 条，没露出来。

## 修法：让 bvid 进 SQL，不留前端筛

```python
sql = "SELECT * FROM publish"
args = []
if bvid:
    sql += " WHERE bvid = ?"
    args.append(bvid)
sql += " ORDER BY id DESC LIMIT ?"
args.append(limit)
```

不在前端筛，是因为「全局窗口 + 前端过滤」这个组合本身就是错的：窗口按时间截断，而过滤条件按内容，两者不对齐，**窗口一满就必然丢东西**。这类 bug 不会报错，只会让东西静默消失。

四层一起改，`bvid` 从界面一路透传到 SQL：`index.html` → `main.py` 的 `/api/publishes` → `service.list_publishes` → `store.list_publishes`。桌面版走的是 `desktop.py` 的同名方法，也一起补上。

界面上还加了一条：**没有任务时不请求列表**。原来会白拿一份全局列表再筛成空，纯浪费一次查询。

## 顺手修的两处

1. **提示语指向了一个不存在的入口。** 咬合闸门里原话是「要改得先到左边『历史发布』里把那条撤回」——界面上那块叫**发布记录**，`历史发布` 四个字在 UI 里根本搜不到。照着这句话去找，只能找到「历史总结」。已改。
2. **被拦下的记录也发一个「撤回」按钮。** 被拦下/失败的记录没有 `rpid`，点了只会弹一句「无法撤回」——那是在骗人点。现在只有 `status === "published"` 的行才有按钮。

## 验证

- `node tests/frontend_test.js`：**217 通过 / 0 失败**
- `tests/smoke_test.py`：**离线 40/40、HTTP 49/49**
- 新增 6 条 HTTP 断言，钉住「只给索引不给正文」「bvid 过滤」「未知 bvid 回空数组」「limit 上限」这些行为。
- **红绿对照**：把 `bvid` 参数从请求里撤掉，新加的断言立刻变红——断言测的是真行为，不是给代码拍张照。
- 真实数据核对：拿本地 38 条记录跑「旧查询 / 新查询」两套口径，上表那三个视频的结果就是跑出来的，不是推的。
