# bili-scribe token 预算实测

用一条真实的 4 小时直播视频（aid 100000000000001，14363 秒）量出来的输入 token 构成。
所有数字都有出处，没有估算成分。

## 实测输入

| 量 | 值 | 怎么来的 |
|---|---|---|
| 素材正文 L | **40,918 字符** | 重新采集那条视频的字幕正文 |
| 分块 | **7 块**：6×6246 + 5842 = 43,318 字符 | 用真实的 `_split` 跑 |
| 字符→token | **1 字符 = 0.731 token**（1.368 字符/token） | 3000 字真实素材，实测 `prompt_tokens=2193` |
| 笔记 N | **19,772 字符** | 实测第 1 块 3454 + 第 7 块 2195，均值 2824 × 7 |
| draft（总结 JSON） | 4,513 字符 | 数据库里的 `summary_json` |
| 角色提示词 | wengao：system 1052 / critique 219 / revise 137 字符 | 读代码 |

## 真值表

**角色 wengao（文稿编辑，三轮回）：**

| 环节 | 输入内容 | 输入 tokens |
|---|---|---|
| 7 段预读 | 43,318 字符素材 + 1,365 字符提示开销 | **32,663** |
| 归约 | system 1456 + 模板 687 + 笔记 19,772 | **16,020** |
| 自我批判 | system 219 + 笔记 19,772 + draft 4,513 | **17,928** |
| 修订 | system 1456 + revise 137 + 诊断 1200 + 笔记 19,772 + draft 4,513 | **19,817** |
| **合计** | | **86,428** |

**对照 · standard（单轮）** = 32,663 + 15,182 = **47,845**

## 两条从表里读出来的结论

**一、成本大头是"三轮回把同一份笔记送了三遍"，不是预读。**

```
预读      32,663  (38%)
三环合计  53,765  (62%)   ← 归约 + 批判 + 修订，每环都带着完整的 19,772 字符笔记
```

所以要砍成本，杠杆在**轮数**，不在别处。

**二、分段预读的压缩比只有 38–55%，笔记几乎和素材一样长。**

原因是 `MAP_SYSTEM` 明确要求「笔记要能让人仅凭它还原这段内容，不要压缩成一堆
语义模糊的关键词」。这是**刻意的设计**，不是 bug——但它意味着预读这一步
省不下多少，真正的开销在后面的复用。

## 加画面帧的影响（帧只进归约那一次调用）

单张抽帧拼图 = **1,224 image_tokens**（接口自动缩到约 1M 像素后的实际计费）。

| 帧数 | 帧的 token | 三轮回角色 | standard 角色 |
|---|---|---|---|
| 12 张（拟定的默认上限） | 14,688 | 86,428 → 101,116（**+17%**） | 47,845 → 62,533（+31%） |
| 18 张（4 小时全送） | 22,032 | 86,428 → 108,460（**+25%**） | 47,845 → 69,877（+46%） |

只看归约那一次调用：16,020 → 30,708（**1.9×**）或 → 38,052（**2.4×**）。

## 延迟（新量到的）

单块预读实测 **43.2 秒 / 27.0 秒**。7 段预读光这一步就要约 **4–5 分钟**，
这还没算归约、批判、修订和帧的下载。
