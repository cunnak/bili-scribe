# bili-scribe

给一个 B站 视频，把它的内容读一遍，写成总结，发到那个视频的评论区。手动选视频、登录、自动评论，这条链是闭合的。

**不满意就接着改**：同一份素材可以反复打磨——写一句"哪里不对"，它只改该改的地方，每一次都是一版新的，旧的都留着、随时能退回去。

一个本地运行的、个人学习研究用途的技术演示项目。

> **[请先读 DISCLAIMER.md](DISCLAIMER.md)。** 本项目与哔哩哔哩官方无关、未获授权；使用的接口不是官方公开能力；自动化操作账号**可能违反平台用户协议并导致账号受限**，风险由使用者自行承担。不支持批量、刷屏、验证码绕过等用法。

## 先看这段：合规与风险

这比功能重要，别跳。

**接口不是官方的。** B站 开放平台（open.bilibili.com）对个人开发者开放的是视频稿件管理、创作者数据、直播互动、消息推送，**没有发表评论的接口**，也没有视频字幕的出口。所以这个工具走的是 Web 端接口。

**参考文档的母库已经关停。** 2026 年 1 月 28 日，长期作为社区接口依据的 `SocialSisterYi/bilibili-API-collect` 收到 B站 委托律所的律师函后永久下线并删除文档，指控理由是"对哔哩哔哩平台非公开的 API 接口及其调用逻辑、参数结构、访问控制及安全认证机制进行系统性收集、整理，并以技术文档、代码示例等形式向不特定公众传播"。这个项目把接口路径当作本地自用实现细节，不打包分发、不写成教程。

**自动发评论可能违反用户协议，也有封号风险。** 只用在自己的账号上。

**这个工具刻意不做的事：**

- 不绕过评论验证码。碰到 `12015` 就停下来，让人去网页端手动处理。
- 不做多账号轮换、不做批量评论列表、不做定时刷评。
- 不共享凭据、不上传凭据、不把接口包装成对外服务。
- 不在评论区塞外链或话题标签——那些是典型的垃圾评论特征。

**默认有人工确认。** 总结生成后停在预览页，你过目、可以改、勾选确认，评论才会发出去。想全自动可以关掉，但别关。

## 快速开始

```bash
cd bili-scribe
python -m venv .venv
.venv\Scripts\activate          # macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt

copy config.example.yaml config.yaml   # 然后把 llm.api_key 填上
python run.py
```

浏览器会自动打开 `http://127.0.0.1:8818/`。想先确认环境有没有问题：

```bash
python run.py --check
```

它会检查 api_key、数据目录可写性、二维码库、加密库和应用导入，把"跑起来才发现"的问题提前暴露出来。

### 操作顺序

0. **配模型**：切到右上角「设置」，填 `base_url` / `api_key` / `model`，点「测试连接」确认通了再保存。不做这步，总结会因为缺 key 直接失败。
1. **登录**：点「获取登录二维码」，用 B站 App 扫码确认。成功后凭据加密存到本机。扫码走不通时，展开「手动填 Cookie」贴 `SESSDATA` 和 `bili_jct`。
2. **选视频**：粘贴链接、`b23.tv` 短链、BV 号或 av 号。带 `?p=3` 就总结第 3 P。
3. **（可选）传字幕**：视频没有字幕时，在同一步选一份 `.srt` 文件。解析结果会当场回显（段数／时间范围／编码），确认没问题再提交。详见「自己上传字幕」。
4. **等总结**：进度面板会逐条列出每个素材源拿到了什么、为什么没拿到。
5. **确认**：右侧看预览，评论正文可以直接编辑，字数实时校验。勾选确认后发布。
6. **不满意就接着改**：在预览页写一句"哪里不对"，点「再改一版」。改完是新的一版，旧版都留着。详见「迭代打磨」。
7. **可撤回**：发完的记录在左下角，随时能撤回，撤回后能重新发。注意：**评论发出去之后就不能再迭代了**（B站 的评论不能编辑），要改得先撤回。

## 用快捷方式打开（Windows）

**双击 `start.bat`**（或桌面上的 `bili-scribe` 快捷方式）就够了。一次点击把前后端一起带起来：

| 你看到的 | 是什么 |
|---|---|
| 一个控制台窗口 | **后端**。里面是服务日志，`Ctrl+C` 就能停服务 |
| 自动打开的浏览器页面 | **前端**。操作界面 |

启动脚本把三件事串在一起：

1. 没有 `.venv` 就自动创建虚拟环境（需要已安装 Python 3.10+）
2. 自动安装依赖
3. 启动服务，**等服务真的能响应之后**再打开浏览器

**首次运行会慢**：要建环境装依赖，大概一两分钟，需要联网。进度和报错都在那个控制台窗口里——这正是它不隐藏的原因。装依赖失败的样子和不启动完全相同，不给可见反馈会让人以为程序坏了。

### 可以放心重复双击

如果服务已经在跑，再双击一次**不会崩、也不会起第二个进程**：它会认出这是自己，直接把页面打开。端口被别的程序占着时，会明确报出被占用并建议换端口，而不是甩一句看不懂的 `address already in use`。

打开浏览器也不再是"固定等 1.2 秒"，而是**轮询到服务真能响应为止**（最多 25 秒）。机器慢的时候不会打开一个打不开的地址。

### 想让它安静点

`scripts\create-shortcuts.bat` 会在桌面生成两个 `.lnk`：

| 快捷方式 | 行为 |
|---|---|
| `bili-scribe` | 静默启动，不弹控制台 |
| `bili-scribe-debug` | 带控制台，等同于 `start.bat` |

静默模式没有窗口可关，用 `stop.bat` 停：

```bat
stop.bat            :: 停默认端口 8818
stop.bat 8819       :: 停自定义端口
```

它会找出占用该端口的进程、结束它，然后确认端口确实已释放。

## 分享给别人

把整个 `bili-scribe` 目录打包发过去就行。对方那边需要：

1. **自己装 Python 3.10+**（安装时记得勾 "Add python.exe to PATH"）
2. 解压后双击 `start.bat`
3. 在界面里**用自己的 B站 账号扫码登录**，在 `config.yaml` 里**填自己的大模型 api_key**

三条都不可省略，也没有办法替对方省掉——每个人用各自的账号和各自的模型额度，本项目不涉及任何凭据共享。

打包时应当排除：`.venv/`、`__pycache__/`、`config.yaml`、`*.db`、`key.bin`。这些要么是机器相关的，要么含你自己的登录凭据。

想自己打一个干净的发布包：

```bash
python scripts/package.py
```

会在 `dist/` 下生成一个 zip，已经排除了上面这些内容。

## 出问题先看这里

### 先看页面最下面那行版本号

界面底部常驻一行 `bili-scribe 0.4.2`，**版本号来自后端**（`/api/config`），前端不另抄一份——抄一份就会出现过期的数字，而过期的那个往往就摆在界面上。连不上后端时它不猜，直接写「未连上后端，版本未知」。

它回答的是一个很具体的问题：**"我现在跑的到底是哪一版？"**

- **"文档里说有，我这没有"** —— 先看这一行。多半是本地这个进程还是旧代码：`python run.py` 时窗口标题/启动横幅也印着版本号（`bili-scribe 0.4.2`），对不上就是没重启。停掉旧进程再起一次，代码就换过来了（`git pull` 之后尤其要重启，Python 不会热加载）。
- **它写着"未连上后端"** —— 说明页面不是从 `http://127.0.0.1:8818/` 打开的，或者后端已经退出。见下一条。

### 按钮点了没反应，二维码出不来

九成是下面两种之一。

**一、页面没有被后端托管。** 双击 `index.html` 打开，或者从某个预览面板里打开，它就是一个静态文件——所有按钮都不工作，因为 `/api/...` 根本不存在。现在页面会自己在顶部弹一条红色横幅把这件事说清楚，并把按钮置灰。

正确打开方式是从 `http://127.0.0.1:8818/` 进。`python run.py` 会自动帮你打开浏览器。

**二、缺 `qrcode` 或 `Pillow`。** 这两个只是扫码通道的依赖，缺了应用照样能启动、手动填 Cookie 也照样能用，所以特别容易被忽略。此时界面会把扫码按钮置灰、给出安装命令，并自动展开 Cookie 兜底面板。

```bash
pip install "qrcode[pil]"
```

### 一次性自检

```bash
python run.py --check
```

逐项报告 api_key、数据目录写权限、qrcode、cryptography、应用导入。有一项不过就以退出码 1 结束。

### 其他常见报错

| 现象 | 通常是 |
|---|---|
| 双击快捷方式后窗口一闪就没了 | 服务本来就在跑，它会直接打开页面。想确认就访问 `http://127.0.0.1:8818/` |
| 提示端口被占用 | 有别的程序占了 8818。换端口：`python run.py --port 8819` |
| 浏览器打开了但页面打不开 | 服务还没启动完。现在会自动等它就绪，若仍如此请用 `bili-scribe-debug` 看日志 |
| 服务停不掉 | 静默模式下没有窗口可关，运行 `stop.bat` |
| `-352`、字幕恒为空 | 登录态失效，重新扫码 |
| `-101` nav 未识别到登录态 | Cookie 过期，或手工填时漏了 `bili_jct` |
| `12015` 需要验证码 | 去网页端手动发一条评论解除。本工具不绕过验证码 |
| `12051` 重复评论 | 本地记录被清但评论还在，先去评论区删掉那条 |
| 总结一直是"素材未覆盖" | 该视频既无字幕也无弹幕，只剩标题简介 |
| 模型报 `Model not exist` / `model_not_found` | 模型名写错（大小写和连字符都算）。用 `GET {base_url}/models` 列一遍，或者点设置页的「测试连接」 |
| 模型报 `Access denied by API-Key restrictions` | 模型名没错，但这把 key 没被授权用那个模型。换一个被授权的 |
| 模型请求超时（`Read timed out`） | 多半是思考模型。把设置页的 `thinking` 改成 `off`，见下节 |
| 总结生成成功但内容是空的 | 同上，输出预算被思考吃光了 |
| `ProxyError` / `Tunnel connection failed: 502` | **先看这一条**——模板见下。它长得像"模型服务挂了"，其实请求压根没出去 |
| 模型站点直连超时（`ConnectTimeout`） | 该站点的 DNS 被污染，直连必然连不上。在设置页的 `proxy` 里填代理地址 |

### `ProxyError` / `502 Bad Gateway`：看起来像模型挂了，其实是代理

完整报错长这样：

```
模型请求失败：HTTPSConnectionPool(host='xxx.com', port=443): Max retries exceeded
(Caused by ProxyError('Unable to connect to proxy',
 OSError('Tunnel connection failed: 502 Bad Gateway')))
```

关键在 `ProxyError`——**请求被送进了一个代理，而那个代理连不到目标站点**。跟模型服务本身没关系。

这个坑的成因值得知道，因为它很难查：`requests` 默认 `trust_env=True`，会读 `HTTP_PROXY` / `HTTPS_PROXY` 环境变量。于是"程序走不走代理"实际由**启动它的那个进程环境**决定——从带代理的终端里启动，所有模型请求就被塞进那个代理，而配置文件里看不到任何异常。这不是配置错了，是**行为不可预期**。

所以这个版本的客户端做了两件事：

1. **`trust_env = False`**：代理**只能**来自 `llm.proxy`，绝不来自环境变量。
2. **代理失败时把话说明白**：错误信息里带上当前代理地址，并提示"这通常不是模型服务的问题"。

排查顺序：先确认 `llm.proxy` 是不是你以为的那个；再确认这个代理能不能连上 `base_url`；都不行就先留空试直连。

### DNS 被污染的站点必须走代理

有些站点在本机**直连一定失败**，因为域名被解析到无关的境外 IP。实测 `aihubmix.com` 被解析到 `31.13.86.21`（Facebook 的地址段），于是：

| 路由 | 结果 |
|---|---|
| 直连 | `ConnectTimeout`（24 秒才放弃） |
| 走一个连不到它的代理 | `502 Bad Gateway` |
| 走能连上它的代理 | **200，1.5 秒** |

判断方法：直连报 `ConnectTimeout`、同时别的国内站点正常，就基本可以确定是 DNS 问题。这时候去设置页把 `proxy` 填上，例如 `http://127.0.0.1:7897`。

`proxy` 只作用于模型请求；抓 B站 的请求不经过它。

## 思考模型：一个不看 usage 就发现不了的坑

部分模型（Qwen3 系列、QwQ、带 `-thinking` 的型号等）会**先产出一大段推理再作答**，而这段推理**不受 `max_tokens` 限制**。

实测数据（`qwen3.8-omni-flash`，素材 19440 字符，`max_tokens=4096`）：

| thinking | completion_tokens | 其中思考 | 耗时 | 返回正文 |
|---|---|---|---|---|
| 开（默认） | **5125** | 5120 | **49.5 秒** | **`[]`（空）** |
| `off` | 793 | 0 | **10.1 秒** | 1502 字符正常 JSON |

两个后果都很难查：

- **耗时不随素材长度线性，而是失控**。视频越长，模型想得越久，最后撞上读超时。报错是 `Read timed out`，看起来像网络问题。
- **输出预算被思考吃光，正文返回空**。这个更阴——HTTP 200、`finish_reason=stop`，从响应表面完全看不出异常，只有 `usage.completion_tokens_details.reasoning_tokens` 能举证。

**顺带一提，流式救不了**：实测 `stream=true` 的首字节也要 52 秒才到，这个网关会把整个响应缓冲完才吐出来。

所以：

```yaml
llm:
  thinking: off        # 用思考模型就填这个
  timeout_seconds: 300 # 只是保险，根治靠上面那行
```

设置页里同样能改。填 `auto`（默认）表示不发送任何相关参数，对其他厂商最兼容。**即使填 `auto` 或 `on`，客户端发现"正文为空 + 有思考 token"时也会自动关掉重试一次**——这件事会显示在进度面板上，不会悄悄发生。

## 它是怎么工作的

### 五个阶段

```
输入解析 → 内容采集 → 大模型总结 → 人工预览确认 → 发表评论
                          ↑              │
                          └── 迭代打磨 ───┘     不满意就在这里改，改完再看
```

最后一格会写回本地去重表，所以同一个视频再次请求时，第一步就被拦住了。

### 素材降级链

排序依据是"离视频内容本体有多远"：

| 顺位 | 来源 | 可信度 | 说明 |
|---|---|---|---|
| 1 | **你上传的 srt** | 未知 | 只要你传了就用它，平台字幕让位。来源无法校验，见下节 |
| 2 | 人工字幕 | 高 | UP 主上传或平台校对，最贴近原意 |
| 3 | B站 AI 字幕 | 中 | 语音识别，有同音字和断句错误 |
| 4 | 弹幕 | 低 | 只反映观众反应，**不等于视频讲了什么** |
| 5 | 标题／简介／标签 | 低 | 撑不起内容级总结 |

上传件排在最前是刻意的：你上传这个动作本身就表明你知道自己在要什么，程序不该再自作主张回去用平台字幕。但**不会静默忽略**——平台如果有字幕，来源检查里会如实写明"已让位给你上传的字幕"。

**字幕必须登录才有。** `x/player/wbi/v2` 对匿名请求恒定返回空字幕数组，没有免登录路径——这是实测结论，不是猜测。弹幕反过来，免登录可拿。

这条链全走空时，采集器直接报错退出。不拼凑。一份基于标题和简介编出来的总结看着像模像样，实际上是把模型的先验知识伪装成了视频内容，那比报错糟糕得多。

### 长素材怎么处理

素材超过 `max_input_chars` 就分段预读，每段先出结构化笔记，再拿笔记做归约。分块数有上限（8 段），避免一个长视频把成本炸开。

这份笔记会被留在内存里给后续迭代复用——同一份素材改多少版，预读只付一次钱（见「迭代打磨」）。

### 防止模型编内容

提示词里下了几条硬约束：只用素材里的信息；弹幕必须标明是观众视角；素材不足就写"素材未覆盖"；不评价 UP 主。时间戳只在素材真实出现过时才允许填进 `timeline`，素材没有时间戳就返回空数组。

另外，字幕是按 15 秒时间窗聚合后才给模型的。平台 AI 字幕既没标点又被切得极碎，原样拼进去，模型判不出章节边界，也容易被支离破碎的语序带偏。

### 画面（全片抽帧）

除了文字素材，总结时还会附上若干帧画面。它不下载视频——B站 的 `x/player/videoshot` 只传 aid 就能返回全片抽帧，而且**不需要登录**。

**它是怎么做的**：返回的是一张张 10×10 的网格拼图，每格 480×270、约 14 分钟一格。直觉是把整张拼图交给模型，一次覆盖 100 个时刻；实测否掉了这条路——不缩则 12 张共 15.2 MB（发不出去），缩到能发出去单格只剩 160×90（**画面上的字就糊了，而字正是加画面的全部价值**）。所以这里是**裁单格**：体积只有整张的约 1/88，分辨率还是原生的。

**它挂在哪**：只挂在**最终归约那一次**调用上。帧一旦进入预读或三轮回，同一批图会被反复送好几遍（预读最多 7 次、三轮回再 2 次）。12 帧约 1,464 image_tokens，占一条 4 小时视频总输入的 1.7%；接在归约上就只付一次。

**它值不值，取决于内容类型**——这一点实测得很清楚：

- **有 PPT／图表／代码的讲座**：增量显著。实测一场讲座，画面里印着的 `GRPO (DeepSeekMath, 2024.2)`、`Instruction Tuning`、`Zero-shot`、`V1...R1` 都进了产出，而这些字在素材（弹幕）里一个都没有。
- **纯口播直播（人像小窗 + 字幕 + 壁纸）**：增量接近零。画面上的有效文字就是字幕本身，而字幕我们已有全文。

同一份素材做过对照（带帧 / 不带帧各跑一次，其他条件完全不变）：不带帧时 `caution` 里写着「无法还原 PPT 具体内容」，带帧时那些内容就出现在正文里了。同时画面里**没有**的 `RLHF` / `PPO` / `SFT`，产出里也没有——说明它在按画面实际内容用，而不是凭先验写。

**但它不能消除模型补先验**：画面上只印着 `GRPO` 这三个字母，产出里写成「GRPO（Group Relative Policy Optimization）」——全称是模型自己补的。加画面补的是「信息来源」，补不了「模型会不会在信息上加工」。

**采完就删，而且每次采集独占一个目录**：帧缓存落在 `~/.bili-scribe/frames/<aid>-<随机>/`，**由这次采集自己建、自己删**，成功失败都删。画面在返回前已经进了内存（base64 直接随请求发走），所以那些 jpg 从那一刻起就没用了。它是整条链路上唯一会把第三方内容实体落到本地的东西，没理由多留一秒。另外启动时和每个任务开始时都会兜底清一次超过 2 小时的残留（崩溃／被杀留下的）。

目录名里那个随机后缀不是装饰。早先是按 `<aid>` 命名的，于是**同一个视频的两次采集共用同一个目录**，而"上一次任务的收尾"会把这个 aid 的目录整个删掉——正好撞上"这一次任务刚开始往里写"，结果是**偶发的** `FileNotFoundError`（实测复现率约 1/6），现场看起来像网络抖动。根因不是删得早晚，是两次采集共用了同一个东西；改成各自独占之后，这一类竞争从构造上就消失了。同一批逻辑还有一个更隐蔽的版本：两个任务同时总结同一个视频，也会互相删对方的画面。

配置在 `collect.frames`：`enabled`（默认开）、`max_frames`（默认 12，等距铺满全片）、`quality`。

### 自己上传字幕（srt）

视频没字幕时（无字幕的讲座、课程录像最容易遇到），可以在主页选一份 srt，让总结基于你自己准备的字幕。**传了就用它**，平台字幕让位——但"平台其实有字幕"这件事会如实写进来源检查，不会静默忽略。

**选完立刻给回执**，不用等任务跑起来才知道文件对不对：

```
lecture.srt：解析出 717 段，覆盖 00:00:00–01:59:23（编码 utf-8-sig）。这份字幕会优先于平台字幕使用。
```

回执里**回显识别到的编码**是有用的——出现乱码时那是唯一的线索。支持的编码：UTF-8（含 BOM）、gb18030／GBK、UTF-16、big5，自动探测。

**不做 15 秒时间窗聚合。** 平台 AI 字幕没标点、几字一行，聚合是为了救它；而 srt 通常已经是规范整句，再按 15 秒粘合会把独立对话并成一坨，甚至把两句话拼成一句。你上传的文件按原样分句。

**时间轴能生成**：srt 自带真实时间戳，`timeline` 会照它填——这是上传件的一个实际优势，纯标题／简介素材是生不出时间轴的。

**两条错配校验，只警告不阻止**：字幕覆盖时长不到视频的一半 → 提示"可能只覆盖了一部分"；最后一条的时间超出视频时长 1.2 倍 → 提示"时间轴与视频不符，可能传错了文件"。不阻止，是因为分段上传、只讲了一部分的录像都是合法场景——但这类错误一旦发生，总结会错得很隐蔽，所以必须让它出声。

**用完就删**：上传的文件落在临存区，任务结束时删除（**失败的任务同样删**），另有启动时与每个任务开始时的兜底清理，收走"传了但没提交任务"的那些。任务记录里只留「你上传的字幕 + N 段」这一行标记，不存文件本身。

**一个无法消除的局限**：srt 格式里不含任何视频标识——没有 bvid、没有标题，只有一串时间轴。所以**程序没有办法真正验证"这份 srt 属于这条视频"**，只能拿时长去比。两条视频时长接近时（同一系列的两集、同一场讲座的上下半场），校验会直接通过，而模型会拿 A 的字幕去总结 B——这类错误不报错、产出读起来通顺，**只有你自己发现"讲的内容对不上"才能察觉**。选文件时留意版本。

技术细节在 `bili_scribe/core/srt.py`（解析与编码探测）和 `bili_scribe/infra/uploads.py`（临存区）。

### 迭代打磨（改到满意为止）

第一次生成的总结不满意，就在预览页写一句"哪里不对"，点「再改一版」。改完是**新的一版**，旧的都留着。

**形态上它刻意不是「重跑一次，顺便加个提示词」。** 那种做法有三个问题：

1. 提示词只改「怎么讲」，改不了「讲什么」。如果你不满的根源在素材层（漏抓、聚合掉了），加提示词会**掩盖真实原因**，让你反复花钱而天花板根本不在那儿。
2. 每次都是全量重跑——4 小时视频一次 86,428 tokens。
3. **全局提示词会把你已经满意的部分也重写掉**。每一轮都在破坏上一轮的成果。

所以这里是「**素材 + 上一版 + 本次要求**」：模型看到完整的上一版 JSON 和你的要求，被明确告知**只改需要改的地方**。

```
不满意 → 写一句要求 → 只改该改的 → 新的一版 → 再看
                        ↑                      │
                        └────── 反复 ──────────┘
```

**省下的是预读那一段。** 长素材要先分段预读（见「长素材怎么处理」），它实测占一次 4 小时视频总结输入的 **32,663 tokens / 38%**。迭代时这份笔记直接复用：活体验证的轨迹里**没有 `mapping` 那一步**——不是"耗时变短了"，是那一步根本没发生（那次对照把字数上限临时调小，好让"预读到底有没有跑"放大到看得见，于是 168.2s → 36.1s）。素材笔记因此**只放在内存里**：它是第三方内容的衍生品，丢了重新预读就能重建（只是贵一点），没理由长期躺在磁盘上——和画面帧、上传件「用完即删」是同一条取舍。

**但版本史必须落库，因为它不可重建。** 靠重跑模型拿不回同一段文字——那是丢劳动，不是丢缓存。所以每一版（初版／每次迭代／每次回退）都进 `summary_version` 表，服务重启后一版不少，每版的全文、发布长文、当时的消耗、当时的要求都能查回来。

**回退不等于撤销。** 点「以这一版为底稿」，是把那一版的内容抄成**新的当前版**（版本号继续往前），而不是把指针挪回去——版本史要能如实回答"当时实际用的是哪一版"，这和 git revert 是同一种取舍。回退**不调用模型**：实测 0.03 秒、零消耗，累计消耗也不会涨。

**消耗是要看的。** 预览页顶部常驻一行"这条视频累计：N 次模型调用 / 输入 X、输出 Y、合计 Z tokens"，每一版各自花多少也在版本列表里。不设硬上限——设了就变成"改到一半被拦住"，比多花点钱更糟——但让代价一直可见。端点不返回 `usage` 的调用会被单独点出来（"N 次端点未返回用量"），不给一个漂亮的 0 蒙过去。

**角色是锁定的。** 迭代沿用上一版那次用的角色——换角色等于换个人重讲，那就不是打磨了，得重新提交任务。

**改完会重新要求你确认。** 内容变了，"已确认"就不作数了：每次迭代后确认勾选会自动清空。

**入口只在发布前。** B站 的评论发出去不能编辑，所以发布之后打磨入口会关掉并说明原因——想改就得先在「历史发布」里把那一条撤回。发布后的"改一版"其实是"撤回重发"，性质变了，所以不让它藏在同一个按钮后面。

**一个必须知道的局限：`revise_note`（改动说明）是模型自己写的，未必与实际改动一致。** 实测抓到过两次——一次它写"保持原样"，实际改了条数；一次要求明确写着"只改 one_line、其余四个字段一个字都不要动"，那四个字段确实逐字未变，但它顺手改了第五个字段，而说明里也承认了。

**所以每一版旁边还有一行"实际改动"，那是算出来的，不是它说的。** 把这一版和上一版的 JSON 逐字段比一遍（纯本地、零成本），列出真正变了的字段、变了多少。它和"改动说明"的分工是：**说明是模型的意图（线索），实际改动是事实（可核对）**——两者不一致时，以后者为准。

想看**具体差在哪里**（到底改成了什么），两个办法：鼠标停在那一行上；或者点列表上方的「**展开全部差异**」把每一版的差异都铺开。那两个办法不是重复的——**行里只有字段名和量级，"改成了什么"才是判断这次改动能不能接受的依据**，所以只把它藏在悬停里，等于对这个功能对不悬停的人不存在。开关只在真有差异可展开时才出现（没有差异却摆一个点不动的按钮，是假入口）。

三种状态分开说，因为它们完全不同：

| 显示 | 含义 |
|---|---|
| （不显示这一行） | 没比过：第 1 版没有上一版；回退版没有"改"这回事 |
| `无 —— 和上一版逐字相同（要求没被落实）` | 比过了，一个字没变——**这本身就是信息**：你的要求没落地 |
| `正文（1279 → 1322 字，相似度 0.93）· 要点（6 项 → 6 项，其中 1 项内容不同）` | 逐字段列出 |

只报**内容字段**（一句话结论／正文／要点／时间轴／局限说明／短版）。`chunks`／`model`／`frames` 这些元信息变了不算"内容改动"——混进来会让每次比对都显示"改了一堆"，那等于没有信号。列表字段会额外说出"有几项内容不同"，因为最常见的情况恰恰是**项数没变、内容被换掉了**（就是上面那个实例）。

### 总结角色

主页提交前可选的「总结角色」，决定总结的**风格与组织方式**。设置页里能改默认值。

| key | 名称 | 轮次 | 特点 |
|---|---|---|---|
| `standard` | 标准 | 1 | 不套方法论，最克制 |
| `xueshu` | 学术分析 | 3 | 重建论证链条，区分「作者的主张」与「作者引用的证据」 |
| `renhua` | 说人话 | 3 | 一个锚点撑全文、推理外显、变形替代定义 |
| `shensi` | 超强思考模式总结 | 3 | 正文就是四问：作者提出的问题／内容的实质／他给出的解法／他发现了什么 |
| `wengao` | 文稿编辑 | 3 | 扩写型，产出最长，适合发笔记 |
| `xiezuo` | 写作专家 | 3 | 四重心法，重结构与节奏 |
| `fenxi` | 分析报告 | 3 | 八部分结构的长报告 |
| `jinglian` | 首席思想精炼师 | 3 | 抛弃原序，重提炼 |

除「标准」外都是**三轮回**：生成 → 自我批判 → 按批判修订。三次是独立调用，批判和修订都能看到原始素材——否则三轮只是走形式。

**角色不能覆盖底线。** 每个角色的提示词后面都会拼上输出契约与硬约束（只用素材、素材不足就写「素材未覆盖」、不评价 UP 主）。角色只管风格，不管事实来源。所以像「说人话」这种主动舍弃信息换可读性的角色，会要求它在 `caution` 字段里交代自己舍弃了什么。

### 超强思考模式总结（`shensi`）

这个角色的**正文骨架是使用者指定的**，只有四节，标题不许改：

```
## 作者提出的问题   ## 内容的实质   ## 他给出的解法   ## 他发现了什么
```

它的两个方法来源值得写出来，因为它们决定了每一节怎么写：

- **「作者提出的问题」用斯金纳式的方法还原**：问题先于答案，而问题比答案难写——答案是作者会说的（它甚至写在标题里），问题是作者假定你已经知道的。所以入口是**先找他在跟谁较劲**：他在反驳谁、纠正哪个流行说法、什么事让他非说不可。问题从敌意里露出来。
- **「实质」是承重墙**：写他真正断言了什么，判据是「这句话如果被证伪，整条视频就塌了」。题目是包装，实质是承重墙。另外三节的判据分别是——**解法要分对象**（给个人的／给制度的／给同行的；只有诊断就说"它停在诊断上"）、**发现要分清新事实与新解释**（绝大多数视频没有新事实，只有新解释）。

**遇到没有明确论点的视频**（直播闲聊、切片、状态记录）：可以替作者归纳一个他没说出口的问题，但必须写明这是归纳出来的、并指出**素材里哪一处**支撑它；指不出就退回「素材未覆盖」。这条由批判轮专门盯——**替作者说出他没说的话，是这一行最容易产出的漂亮错话**。

**文体纪律是具体到形态的**，不是"要真诚"这种话：禁过渡句（"接下来我们看看""综上所述"）、禁评价句（"深刻地揭示了""令人深思"）、禁对称壳子、禁排比撑气势、禁用抽象名词顶替具体事实；正面要求是奥威尔那两条——**能删掉一个词就删掉**，以及**好文章像一块玻璃窗**。

批判轮被**刻意限定**在两个目标上（文体的套话、有没有替作者立论），并明确要求它别按自己的清单去挑内容毛病——否则它会顺手把使用者指定的四节结构改掉（这个坑踩过）。但它必须点名检查**要点与引用**：活体验证的第一版就栽在这里，模型把截断的原话碎片（夹着语音识别把英文转成的乱码）直接当成了 `key_points`，而那一轮当时看不见。

> 改好之后跑过两次真实生成（同一场 30 分钟视频）：四节骨架都在、套话形态 0 命中、要点变成了提炼过的判断。**但模型的服从度不是 100%**：第二次那版 `comment_short` 写了 317 字，超出它自己的 180–280 字规格；还有一处引语里留着语音识别的乱码数字（"十456岁"）没处理——规则要求"要么改对、要么在 caution 里说明"，它两样都没做。这类偏差现在只能靠迭代打磨或人工发现。

角色定义全部集中在 `bili_scribe/core/roles.py`，改提示词不用碰别处。返回结构、三轮回触发条件、底线拼接都在 `core/summarizer.py`。

## 三道发布闸门

评论是这个应用里唯一不可撤销的动作，所以约束最多。

**人工确认。** `require_confirm` 为真时，没有显式确认一律不发。

**本地去重。** 发请求之前先查本地记录。B站 对相同内容重复发送返回 `12051`，与其等平台拒绝，不如自己先拦住。同一视频只允许有一条未撤回的评论。

**频率限制。** 两次发布之间强制间隔，默认 60 秒，避免踩到 `-509` 限流。

### 评论错误码速查

| 码 | 含义 | 本工具的处置 |
|---|---|---|
| `-509` | 请求过于频繁 | 退避重试最多 2 次 |
| `-111` | csrf 校验失败 | 提示重新登录 |
| `12015` | 需要评论验证码 | **硬停**，请去网页端手动处理 |
| `12016` | 内容含敏感信息 | 硬停，提示改措辞 |
| `12025` | 评论字数超限 | 组装阶段已按 `max_comment_chars` 裁剪 |
| `12035` | 被 UP 主拉黑 | 硬停 |
| `12051` | 重复评论 | 本地去重应已前置拦截 |
| `12002` / `12052` | 评论区已关闭 | 硬停 |
| `-102` | 账号封停 | 硬停 |

## 配置

两种改法：**页面右上角的「设置」标签**，或者直接改 `config.yaml`。两边用的是同一份文件，改哪个都一样。

### 用页面改

界面上能调所有可调项，改完点「保存设置」**立即生效，不用重启**（只有 `host` / `port` 例外，那两项改了要重启）。

- **保存前自动备份**：原文件会复制一份 `config.yaml.bak`，写坏了可以自己覆盖回来。
- **注释不会被吃掉**：回写时按带完整中文注释的模板重新渲染，文件始终是给人看的。
- **密钥默认掩着**，点「显示」才展开。清空那一格再保存等于删掉密钥。
- **「测试连接」用的是表单里当前的值**，不写盘——可以先试好一个 key 再保存。

保存时后端会自己再校验一遍，不靠前端拦：`chunk_overlap` 必须小于 `chunk_size`、评论长度不能超平台上限、关闸必须显式确认。

### 直接改文件

```yaml
llm:
  base_url: https://api.deepseek.com/v1
  model: deepseek-chat
  thinking: auto            # 思考模型填 off。理由见上面那节，这是个真会咬人的坑
  timeout_seconds: 300
  proxy: ""                 # 留空＝直连，且不读环境变量里的代理。需要时填 http://127.0.0.1:7897
  role: standard            # 默认总结角色，主页面上还能对单次任务临时改
  max_input_chars: 24000    # 超过就分块归约

collect:
  danmaku:
    also_with_subtitle: false   # 有字幕时是否也抓弹幕，开了会明显增加 token 消耗

publish:
  require_confirm: true       # 别改
  min_interval_seconds: 60
  disclose_ai: true           # 在评论里注明 AI 生成
```

`base_url` 只要兼容 OpenAI 的 `/chat/completions` 就能用，不绑定厂商。

`proxy` 留空表示直连，**并且不读 `HTTP_PROXY` / `HTTPS_PROXY` 环境变量**——这是有意的，理由见上面「`ProxyError` / `502 Bad Gateway`」那节。它只作用于模型请求，抓 B站 的请求永远直连。

### 关于人工确认闸门

设置页里能关掉它，但那要走两道确认：勾选"我知道后果"，后端还会独立校验一次这个标志位。**关掉之后总结一生成就直接发到对方视频的评论区，没有中间环节，发错了只能自己去评论区删。** 留着它是有意的——这是整个项目里唯一不可撤销的动作。

关掉之后顶部会常驻一条红色横幅提醒你，它不会自己消失，只能回设置里把闸门重新打开。

### 跑测试

```bash
python tests/smoke_test.py     # 33 项离线 + 35 项 HTTP
node tests/frontend_test.js    # 134 项前端
```

`smoke_test.py` 会真的去请求一次 B站 的扫码接口（匿名取码，不涉及登录），并在临时目录里跑一遍设置页的完整读写——它在结尾会断言项目的 `config.yaml` 一个字节都没变，因为这个测试是真的会写配置文件的。

它还会强制 `NO_PROXY=127.0.0.1,localhost`：整套 HTTP 探测都打本机，如果让 `requests` 去读环境变量里的代理，请求会被送去让代理转发回 localhost，而代理通常连不回来——测试结果就会随启动它的那个 shell 变化。被测对象是应用，不是 shell 的环境。

前端那 134 项里，A 组专门盯着"页面没连上后端"这个出过事故的场景，B 组钉住"页脚显示的版本号必须是后端报的那个"（夹具故意用一个不存在的版本号 `9.9.9-探头`，前端要是自己抄了一份版本号就会露馅），F 组盯设置页的字段名与后端逐个对齐（对不上就会被静默忽略：保存"成功"但配置没生效），G 组盯上传字幕那条入口，H 组盯迭代打磨（要求为空不能提交、缓存失效时把原因显示出来而不是给个点不动的按钮、翻看历史版时发布区必须收起来、迭代完成后确认勾选被重置、回退走的是哪个接口、「实际改动」的三种状态各说各的话、「展开全部差异」开关的开与关、以及刷新列表后它不会被弹回去）。

还有一条「**上传入口可辨识**」值得单说：它读 HTML 源码并**实际计算对比度**，断言上传按钮与页面底色的对比度不低于 3:1。起因是一次真实反馈——"页面上找不到选择字幕文件的选项"，查下来元素在、JS 也对，只是样式用了几乎等于底色的深色边框（对比度约 1.4:1），在深色页面里融进了背景。**这类缺陷 DOM 桩永远抓不到**：桩里 `getElementById` 对任何 id 都凭空返回对象，"元素在不在"它一律答"在"。所以这条只能靠读源码 + 算数来守。

值得单说一条：**「上传解析不阻塞事件循环」测的是实现方式，不是行为。** 它断言接口把解析与落盘交给了线程池——因为 `/api/subtitle/parse` 是 async 路由，而解析是同步 CPU 操作，实测一份上限体积（5 MB）的 srt 要 0.5–0.8 秒，直接在事件循环里跑会把其他请求（含任务进度轮询）一起卡住。我没找到稳定观测"事件循环有没有被阻塞"的办法（构造精确并发容易 flaky），所以退一步做源码守卫：它能挡住大部分退化场景，比如有人为了简洁把它改回直接调用。

还有一条「**画面文件的生死**」：它用一个假 B站 客户端（自己生成小拼图）真跑 `collect_frames`，断言三件事——采完不留残骸、中途下载失败也不留残骸、**同一个视频并发采两次谁也不许动谁的目录**。第三条是那个偶发 `FileNotFoundError` 的守护：写完之后把目录命名改回旧的"按 aid 共用"，这条用例必然失败（慢的那次报同一个错）。**跑不挂的守护用例等于没写**，所以新写的回归用例都先在旧实现上跑一遍、确认它真的会红。

还有一条「**报错指出出错的那一行**」：它真的去 open 一个不存在的文件，断言任务里记下的错误带着文件名和出错位置。起因是那个偶发失败在库里只留下 `FileNotFoundError(2, 'No such file or directory')`——**没有文件名**，因为 `{exc!r}` 不打 `.filename`。造这个异常的方式也有讲究：手工构造异常会把文件名塞进参数，`repr()` 里就有它了，用例反而测不出问题（第一版就是这么写错的，后来改成真的 open 一个不存在的路径）。

## 凭据怎么存

`~/.bili-scribe/bili-scribe.db` 里存登录凭据，用 Fernet 对称加密，密钥单独放在 `key.bin`。这挡不住能读你整个用户目录的人，但能保证数据库文件被单独拷走时凭据不可读。

没装 `cryptography` 时会退回明文并打印警告——功能优先，但风险要说不出来。

服务只监听 `127.0.0.1`。**别改成 `0.0.0.0`**，这个进程持有你的登录凭据。

## 已知限制

**字幕路径依赖登录态。** 未登录时字幕恒为空，会直接掉到弹幕或元数据档。所以不登录能用，但总结质量会明显下降。

**接口没有稳定性承诺。** 这些路径随时可能变。所有调用点都在检查 JSON 里的 `code` 而不是 HTTP 状态码——B站 大量接口在 200 的情况下返回失败，只看状态码一定会漏判。

**平台侧 AI 摘要只做对照。** `conclusion/get` 能拿到平台自己生成的摘要和分段提纲，界面上显示出来供你比对，但它不参与本次生成，也不会冒充成这个工具的输出。

**没有做自建 ASR。** 无字幕时下载音轨自己转写这条路是通的，而且能彻底绕开字幕权限，但需要额外的模型额度，当前版本没接。现在的替代办法是**自己上传一份 srt**（见「自己上传字幕」）——工具不做转写，但接受你从别处拿到的转写结果。

**上传的 srt 无法验证是否真属于这条视频。** srt 格式里没有视频标识，只能拿时长去比，所以时长接近的两条视频是分不出来的。详见「自己上传字幕」那节末尾。

**硬字幕仍然拿不到。** 抽帧已经做了（见「画面」一节），但那是把画面交给多模态模型去读，不是 OCR——单格只有 480×270，内嵌字幕常糊到不可读；而且要靠它转写整条片的字幕，逐帧读既慢又贵。所以「有硬字幕、但没有平台字幕」的视频，这条路依然补不上——**可行的绕法是在外部做一次 OCR 或转写，把结果存成 srt 传进来**。

**迭代打磨依赖内存里的素材笔记。** 那份笔记只在内存（理由见「迭代打磨」），所以**服务重启过**、或者中间又总结了 200 条以上把它挤出去之后，这条视频就需要重新跑一次才能继续改。界面会把原因如实写在按钮旁边，不会给一个点不动的按钮。**版本史不受影响**——每一版全文都躺在库里，一直在。

> 200 这个数是量出来的，不是拍的：一条缓存实测 **39 KB**（4 小时视频的笔记约 2 万字），最坏（笔记被截到上限的两倍）**94 KB**，200 条约 8–18 MB；而且**原素材不会跟着进缓存**（换成笔记时就丢掉了，实测把素材从 1.2 万字换成 60 万字，占用纹丝不动）。之所以不吝惜这点内存，是因为淘汰的代价是真金白银——重跑一条 4 小时视频要 86,428 tokens。

**已经发出去的总结不能再迭代。** B站 的评论发出去不能编辑，所以发布之后打磨入口会关掉并说明原因；要改得先在「历史发布」里撤回那条评论，改完重新发。

**改动说明不保证准确。** 它是模型自己写的，实测出现过"说保持原样、其实改了"和"顺手改了没被要求改的字段"。所以每一版旁边还给一行**算出来**的「实际改动」（本地逐字段比对，零成本）——两者不一致时以后者为准。详见「迭代打磨」。

**发出去的可能不是任何一版。** 评论正文在发布前**可以手改**，而版本史里存的是模型那一版。手改之后，发布记录里是你改后的文本、版本史里是模型版，而两者之间没有任何字段能把它们连起来（发布记录不记版本号）。所以"我发出去的到底是第几版"这个问题，在现有数据里**可能根本没有答案**——不是不好查。

- 硬字幕 OCR 抽帧
